### Summary

Plan implements synchronous wait mode via `CompletableFuture<WorkflowExecutionEntity>` synchronization between the request virtual thread and the background executor task. Architecture is sound: leverages Java 25 virtual thread carrier-unmounting, preserves the async path verbatim (REG-01), and adds defensive `timeoutSec` clamping plus non-destructive timeout continuation. ### Strengths

- **Async path preservation is faithful.** Task 1's refactor routes both `triggerExecution` (future=null) and `triggerExecutionSync` (future≠null) through `triggerExecutionInternal`, with every `future.*` call guarded by `if (future != null)`. Behavior of the existing async path (`TestWorkflowExecutionService.java:57-96`) is preserved byte-for-byte; `runningTasks.put`/`remove` and `pruneWorkflowExecutionsIfExceeded` both survive. REG-01 test (`WorkflowExecutionNavigationUrlTest.java:67`) covers the regression.
- **Return value of `executeWorkflow` is correctly captured.** Current code at `TestWorkflowExecutionService.java:73` discards the return; plan's refactor assigns `WorkflowExecutionEntity finished = karateRunner.executeWorkflow(...)`. Verified signature returns `WorkflowExecutionEntity` (`DynamicKarateRunner.java:56`). The completed entity carries `reportPath` set during finalization (research cites `DynamicKarateRunner.java:205-210`), so `enrichNavigationUrls` can populate `reportUrl` on the HTTP 200 path.
- **Non-destructive timeout is correctly specified.** Task 3 catch block returns `ExecutionSyncResult(inFlight, true)` without calling `task.cancel(true)` or `DynamicKarateBridge.markCancelled()`. Background virtual thread continues to completion. This directly mitigates T-04-02 and satisfies SYNC-03's "without failing the running execution" clause.
- **Cancellation unblocking is correctly modeled as normal completion.** Task 2's `future.complete(execution)` in `cancelExecution` is a *normal* completion (not exceptional), so `completionFuture.get()` returns the cancelled entity without throwing. The controller's `!syncResult.timedOut()` branch fires → HTTP 200 with `status: CANCELLED`. This matches `must_haves.truths` claim #3. Semantically clean.

Registration (`executionFutures.put`) happens before `virtualThreadExecutor.submit`, so even if the task completes instantly, `CompletableFuture.get()` returns the completed value without blocking. - **Defensive clamping addresses T-04-01.** `Math.max(1, Math.min(timeoutSec, maxWaitTimeoutSec))` with `maxWaitTimeoutSec` injected via `@Value("${orchestrator.execution.max-wait-timeout-sec:300}")` prevents Slowloris-style connection starvation. `application.yml:43-51` already has the `orchestrator:` block; adding `execution:` subsection is consistent with existing `reports:`/`retention:`/`async:` structure.

### Concerns

- **MEDIUM — Transform-step failure path may not populate `reportPath`.** Task 2's `testSynchronousExecutionFailureReturns200WithFailedStatus` uses fixture `failingWorkflow` with script `function(ctx) { throw 'step intentional failure'; }` and asserts `reportUrl` is populated. Two outcomes are possible: (a) `DynamicKarateRunner` catches the script exception internally, marks execution FAILED, generates a Karate HTML report, sets `reportPath`, and returns normally → test passes; (b) the exception propagates out of `executeWorkflow` → `triggerExecutionInternal`'s catch block fires → reads entity from DB, sets `status=FAILED` + `errorMessage`, but does NOT set `reportPath` → `reportUrl` is null → test fails. The plan does not verify which path the transform executor takes. Research does not cite the transform failure-handling code path. **Fix:** Before writing the test, grep `DynamicKarateRunner` and the transform executor for how script exceptions are caught; if (b), either set `reportPath` in the catch block or relax the assertion to `jsonPath("$.reportUrl", anyOf(nullValue(), notNullValue()))` and document the gap.
- **MEDIUM — `testSynchronousExecutionCancellationUnblocksCaller` is underspecified.** Task 2 action says "trigger synchronous execution **or** cancel an in-flight execution registered in executionFutures and verify that cancelExecution completes the future with ExecutionStatus.CANCELLED" — ambiguous about threading. To deterministically test this: spawn a thread that calls `executeWorkflow?wait=true&timeoutSec=10` on `delayWorkflow`, await the request to be in-flight (poll `executionRepository.findById` for `RUNNING`), then call `POST /executions/{id}/cancel` from the test thread, then assert the first thread returns within ~500ms with `status: CANCELLED`. The plan doesn't specify this orchestration. Without it, the test either races (cancel fires before the sync caller parks) or hangs (cancel never fires). **Fix:** Specify the threading harness in the task action; consider `CompletableFuture<Void>` for the request-side block + `Awaitility.await().atMost(2, SECONDS)` for the cancellation assertion.
- **MEDIUM — `timeoutStatus` parameter has no validation.** Task 3's `@RequestParam(value = "timeoutStatus", required = false, defaultValue = "504") int timeoutStatus` accepts any int. The branch `(timeoutStatus == 202) ? HttpStatus.ACCEPTED : HttpStatus.GATEWAY_TIMEOUT` silently maps `?timeoutStatus=200`, `?timeoutStatus=404`, `?timeoutStatus=999` to HTTP 504. A client passing `?timeoutStatus=200` expecting HTTP 200 gets 504 with no error. **Fix:** Either validate `timeoutStatus ∈ {202, 504}` and return HTTP 400 for anything else, or document that only 202 overrides (any other value = 504). The current spec is permissive but undocumented.
- **LOW — `testTimeoutLeavesBackgroundExecutionRunning` polling window is tight.** Delay is 3000ms; test polls up to 5000ms in 200ms intervals (`Thread.sleep(200)` loop). On a loaded CI runner with DB latency, 5s budget for a 3s delay + DB round-trips can flake. **Fix:** Increase deadline to 10s or use `Awaitility.await().atMost(10, SECONDS).until(...)`.
- **LOW — Unexpected exceptions leave `reportUrl` null on the sync 200 path.** `triggerExecutionInternal`'s catch block (`TestWorkflowExecutionService.java:79-87` today, plan's adapted version preserves this) sets `status=FAILED` + `errorMessage` via `saveAndFlush` but never sets `reportPath`. For step-level failures (handled inside Karate) this is fine; for system errors (NPE, OOM, Karate runtime crash) the sync caller gets HTTP 200 with `status: FAILED` and `reportUrl: null`. Not a regression (async path has the same gap), but worth a deviation note in SUMMARY if encountered.
- **LOW — `@Operation` description update not in Task 1 action.** Current endpoint annotation (`WorkflowExecutionController.java:55`) says "Trigger asynchronous execution". After Task 1, the endpoint is dual-mode. Research's code example shows an updated `@Operation` but Task 1's `<action>` doesn't explicitly call it out. Swagger docs will be stale until Task 3 (which also doesn't mention it). **Fix:** Add "Update `@Operation` summary/description to reflect dual async/sync behavior" to Task 1's action.
- **LOW — `ExecutionSyncResult implements Serializable` is decorative.** The record wraps `WorkflowExecutionEntity`, which is a JPA entity not necessarily `Serializable`. The plan only uses Jackson (JSON) serialization, so this is harmless, but the marker is misleading. Match `WorkflowExecutionRequest`'s pattern only if it actually implements `Serializable`; otherwise drop it.
- **LOW — Task 1 ships sync feature without clamping (T-04-01 window).** Between Task 1 commit and Task 3 commit, `?wait=true&timeoutSec=999999` is unguarded. Since all three tasks land in one plan before SUMMARY, the window is internal (no deployment between commits). Acceptable for monorepo atomic merge; flag only if commits are deployed independently.
