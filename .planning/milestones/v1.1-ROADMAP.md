# Milestone v1.1: Execution Status & Report URLs for cURL / CI/CD

**Status:** ✅ SHIPPED 2026-11-10  
**Phases:** 3-5  
**Total Plans:** 4 plans  

## Overview

Milestone v1.1 introduces comprehensive execution tracking, status monitoring, and Karate HTML report discovery for workflows triggered via cURL and external CI/CD pipelines, synchronous wait execution on Java 25 Virtual Threads, and flexible sub-workflow composition with dynamic global flow headers.

## Phases

### Phase 3: Execution Tracking Navigation URLs

**Goal**: Callers triggering or inspecting workflow executions receive absolute navigation URLs (`statusUrl`, `reportUrl`, `streamUrl`) and an HTTP `Location` header to track execution progress and access reports  
**Depends on**: Phase 2  
**Plans**: 1 plan  

Plans:
- [x] 03-01: Enrich execution trigger and details responses with absolute navigation URLs (`statusUrl`, `reportUrl`, `streamUrl`), HTTP `Location` header, and reverse proxy support

**Details:**
- Execution trigger (`POST /api/v1/workflows/{id}/execute`) returns HTTP 202 Accepted with RFC 7231 `Location` response header matching `statusUrl` and body containing `statusUrl`, `reportUrl`, and `streamUrl`.
- Execution details (`GET /api/v1/executions/{id}`) and list endpoints return populated absolute navigation URLs reflecting the caller's request origin.
- Reverse proxy headers (`X-Forwarded-Host`, `X-Forwarded-Proto`) dynamically rewrite URLs via `ForwardedHeaderFilter` without leaking internal container hostnames.
- `ExecutionNavigationUrlBuilder` component provides origin-aware URI resolution.

---

### Phase 4: Synchronous Wait Execution Mode

**Goal**: CI/CD pipelines and automated scripts can trigger workflow execution synchronously via `?wait=true`, blocking until execution completes to obtain final results and report URLs in a single request  
**Depends on**: Phase 3  
**Plans**: 1 plan  

Plans:
- [x] 04-01: Support `?wait=true` and `timeoutSec` parameters on execution trigger for blocking execution in CI/CD pipelines

**Details:**
- Calling `POST /api/v1/workflows/{id}/execute?wait=true` blocks on Java 25 Virtual Threads using non-blocking carrier unmounting via `CompletableFuture.get(timeoutSec, TimeUnit.SECONDS)`.
- When execution completes within timeout, the API returns HTTP 200 with completed execution entity, final status (`COMPLETED` or `FAILED`), and generated `reportUrl`.
- Cancelling execution unblocks waiting synchronous callers immediately (<2000ms) with status `CANCELLED`.
- When execution exceeds `timeoutSec` (defensively clamped between 1s and 300s against Slowloris attacks), the API responds with HTTP 504 Gateway Timeout (or 202) and `X-Execution-Timed-Out: true` header while background virtual thread continues running to completion.

---

### Phase 5: Sub-Workflow Variable Promotion & Global Flow Headers

**Goal**: Enable workflows to include previous/sub-workflows as setup or sequential steps, automatically promoting extracted variables into global workflow settings and headers across both dynamic execution and standalone export  
**Depends on**: Phase 4  
**Plans**: 2 plans  

Plans:
- [x] 05-01: Backend Dynamic Header Promotion, Setup Workflow Execution & Standalone Export Parity
- [x] 05-02: Frontend Setup Workflow Settings, Canvas Badges & Upstream Variable Autocomplete

**Details:**
- Overloaded `DynamicKarateBridge.computeEffectiveHeaders` merges live execution context and dynamically evaluates `${variableName}` tokens in global flow headers before every HTTP request.
- Pre-requisite setup workflow model (`SetupWorkflowConfig`) persisted in AST and `CanvasState`; `DynamicKarateRunner` validates circular self-references and synthesizes a prepended `SUB_WORKFLOW` step at index 0.
- `WorkflowSettingsModal` provides dedicated "Setup Workflow" tab with dropdown, variable promotion mapping table, and "Apply as Bearer Authorization Header" quick-action.
- `SubWorkflowNode` renders visual amber badges for exported variables on canvas.
- `NodeConfigDrawer` computes upstream exported variables from other nodes and renders one-click Sparkles suggestion chips (`+ ${varName}`) across URL, header, and body inputs.
- `TestWorkflowService.generateStandaloneKarateFeature` generates native Karate dynamic JavaScript header callback (`* configure headers = function() { ... }`) and inlines setup workflow steps for 100% execution parity.

## Milestone Summary

**Key Decisions:**
- Dynamic request-origin resolution via `ServletUriComponentsBuilder` producing absolute URLs without environment-specific hardcoded hostnames.
- Framework-managed proxy strategy `server.forward-headers-strategy: framework` activating Spring's `ForwardedHeaderFilter`.
- Non-blocking Virtual Thread carrier unmounting with `CompletableFuture` for synchronous wait execution.
- Defensive parameter clamping (1s-300s) on synchronous wait against connection starvation.
- Per-request dynamic header evaluation via `DynamicKarateBridge` resolving `${var}` tokens against live execution context.
- Zero-migration AST storage in existing PostgreSQL `jsonb` columns for `setupWorkflow`.
- Standalone feature export parity via native Karate JavaScript `configure headers = function() { ... }` callbacks.

**Issues Resolved:**
- Resolved static flow header evaluation that previously evaluated flow headers once before step 1.
- Resolved canvas state persistence dropping `setupWorkflow` and `envSecrets`.
- Synchronized standalone Karate export to support dynamic headers across both `defaultHeaders` and `dynamicHeaders`.

**Issues Deferred:**
- CI/CD Webhook Modal UI enhancements (`CURL-01..03`) deferred to v2.
- Downloadable GitHub Actions workflow template (`CURL-V2-01`) deferred to v2.
- Dedicated JUnit XML / Karate JSON report download endpoint (`CURL-V2-02`) deferred to v2.
